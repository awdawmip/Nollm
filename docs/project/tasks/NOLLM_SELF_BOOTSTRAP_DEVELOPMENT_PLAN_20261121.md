## 1. 目标与交付定义

**让 Nollm 保存和组织对自身的结构理解，让新的开发会话利用这些理解完成真实修改，再将修改造成的知识变化维护回 Nollm，供后续开发继续使用。**

最终交付包括可运行的自身项目记忆、实际开发改动、变更后的记忆维护，以及新会话接续开发的证据。架构调查、目录导入、文档总结都服务于这一交付。

用户明确本系统用于内部理论验证：实现采用受信任内部调用，**删除本次实际调用路径中的防御性代码，不新增冗余验证、哈希自证、签名、认证、审计、通用容灾或回执框架**。普通错误直接暴露并修复。几何、来源、版本和持久化的真实含义以简单实现保留，相关行为测试用来判断系统是否做对了事情。

这份任务规定目标、输入、实际边界和验收结果。开发者自主选择调查、推理、实现及测试方法；里程碑是可观察的交付依赖，不是固定思考脚本。读取范围、表达数量、布局和实验深度由实际问题决定。

## 3. 自举机制：从可用种子开始，以源码和行为校准

用 `C0` 表示起始源码，用 `M0` 表示对该源码形成的持久理解。自举过程的可观察依赖为：

| 前沿 | 需要发生的真实变化 |
| --- | --- |
| `C0 → M0` | Host 直接读必要源码、设计和已有实验，形成足以支撑当前开发问题的自身理解，保存进原生场。种子允许不完整。 |
| `C0 + M0 → C1` | 不携带形成会话上下文的新开发会话使用记忆，回源核对，完成实际补丁和相关行为验证。 |
| `C1 → M1` | 根据代码差分和实际结果，保留、修订、补充有关判断，调整确受影响的位置或连接。 |
| `C1 + M1 → C2` | 另一新会话完成不同的真实开发，其结果需要正确使用 C1 引入或改变的行为；再把新发现保存回场。 |

第一份理解由已有模型和源码产生，不要求 Nollm 先完整理解自己。使用期间，源码、当前有效的设计依据和实际行为结果负责纠正理解。记忆中的“已实现”“已测试”只是有出处的陈述，不能替代当前代码和测试结果。

修改运行时自身时，明确正在运行的版本、被修改的源码版本、场内理解所引用的版本。用现有 Git 和独立进程运行候选；无需开发自升级服务或多代运行时管理平台。若涉及格式变化，在同一普通开发任务中处理实际使用场的读取与迁移。

原生导航暂时找不到材料时，开发者可以继续源码调查，记录该次发现失败并修复对应能力。有效开发继续进行；该次源码救援在效果评价中单独标明。

## 4. 入库内容：保存可以参与开发的工程判断

记忆单元是**一段可独立理解、能回到原文、可以用于判断修改影响的表达**。一条表达可以跨文件，一个文件也可以支持多个不同判断。目录、符号、调用信息和 AOCI 是形成理解的材料。

建议围绕当前实际开发问题组织以下内容；它们是开放的取材方向，不是条目配额或固定分类系统。

| 内容 | 应保存的实质 |
| --- | --- |
| 目标和设计理由 | Nollm 想解决什么；Host、Core、Access 为何这样分工；哪项实现选择受哪些条件约束。 |
| 真实数据流 | 原文、Statement、几何 atom、句柄、current binding、Surface 和回源之间怎样交接。 |
| 跨文件联合条件 | 某个改动为什么需要同时理解多个模块，遗漏另一处会出现什么具体错误。 |
| 关系与差异 | 物理层和观察阶的区别；支持证据与 current 修订的区别；Stitch 的格级传播与语义关系的区别。 |
| 实现与设计的偏差 | 当前代码做了什么，设计原意是什么，差异的实际后果和待验证解释。 |
| 实验与失败 | 来源版本、观察条件、实际结果，以及这些结果能支持哪项后续决定。 |

正文自然表达“设计意图”“当前实现事实”“实验观察”或“待验证假设”。采用已有的 ID、正文、来源和修订机制；不为这些标签另建资格系统、关系类型注册中心或强制多层 schema。

### 工程判断示例

“Surface 的聚合阶是对占用的观察尺度。最终物理入口由 Host 选择，随后 Core 执行有界传播。改变观察阶不会把 Statement 移到另一物理层。因此，修改菜单起始策略时，应检查导航与选择行为，而不是以增加物理层写入解释效果。”

这条表达应引用实际 Surface、导航和调用处的源码窗口。其作用是让未来开发者同时看到观察与传播的边界。

“当前 Core 打开已有状态时，存储层的 validator 已完整解码一次，构造器随后再次解码；解码内部还做字节规范的重复重编码。这是当前实现事实。简化目标是在保存同一状态含义的条件下改为一次读取和解码。”

这条表达引用 `state.py` 与 `storage.py`，并在实现简化后修订为新事实。它不能永远以“current”为名继续描述旧代码。[S7]

上述示例是公开开发材料。针对这些例子的改进属于开发回归；未见任务的效果需要另外选择尚未用于写判断或调布局的实际问题。

## 5. 关系怎样进入 Nollm

继续采用项目现有职责：**Host 决定语义，Core 执行确定性几何与状态，Access 连接命中的句柄与原始证据。**[S1]

同格、邻接、上下 Coverage 用来组织应共同观察的内容；确有用途的远端联系采用现有可逆 Stitch。具体的依赖、限制、可迁移操作及成立条件写在普通表达中，并附双方来源。坐标、传播权重和桥存在本身不承担关系证明。

当前 L0 写入已经能够利用上下层的几何传播，可直接开始自身项目场。语义粒度无需强制对应物理层；观察阶也不新增一层持久记忆。多物理层写入、覆盖数学改造按实际发现另行评估，不是本轮启动条件。

原生发现由 Host 观察 Surface 后选择一个最终物理入口，再沿真实局部与连接展开。正常开发中，精确符号查询可直接使用源码或字面工具；这类查找在评价中按实际机制归类。不要把永久的 `问题→坐标`、`对象→相关对象` 或 `来源→位置` 路由作为原生正确性路径。

当前 Stitch 的端点是物理格：它可能让目标格里的其他表达一起被召回，原位修订也不会自动撤销该桥。Host 应据实际条件判断关系是否继续有用。条件改变时修改关系表达，必要时调用 `unstitch`；不要求每次正文修订都重建全部连接。[S5][S6]

## 7. 明确删除的防御性负担

本节针对 `c685578…` 已读取的源码，给出可直接动手的简化对象。静态重复已经核对，性能改善幅度待实际测量。

| 已观察的代码 | 本轮处理 | 行为验收 |
| --- | --- | --- |
| `state.py:CoreRuntime.__init__` 经 `_FileCoreStateStore.read_bytes()` 触发完整 validator 解码，然后再次 `_decode_state_bytes()`；解码内部又重复重编码比较。[S7] | 合并为一次必要的解码与对象构造；自产状态直接序列化写入，去掉解析自产字节的回路和排版字节自证。 | 现有实际场重开后的 atom、bridge、来源绑定含义不变；保存和原位修订正常。格式不能读取时直接报错，不返回伪造空场。 |
| `kernel_registry.py:KernelRegistry.__init__` 每次对随代码打包的模板计算 SHA；`identity/state_identity` 重算派生摘要。[S8] | 删除逐次模板防篡改自检，收缩重复摘要生成。固定模板行为在改动它时用相关测试核对。已存状态实际依赖的版本标识采用现有格式处理。 | 相同 profile、地址与预算得到预期的几何关系；若只删自证，不改变 Coverage 算法或存储解释。 |

| 旧 `MemoryLoop/Atlas/FieldEncounter` 路径中的整场、页面、区域与 provenance 摘要链；可选 `apply_if_state()` 整场 SHA。[S10] | 自举主路继续用已有薄 API 与直接 `apply()`。实际修改到旧调用链时删除无用证明层和无调用者兼容分支，不把旧链接回新入口。 | 旧页面不会悄悄选择另一个对象，真实写入不会留下半次修订。旧层是否整体退役按实际调用者处理。 |

旧 MemoryLoop 的全部成本并非当前 `research.py` 必经成本。本轮不要将静态存在的复杂代码报告成已测线上开销。

删减按实际用途判断：现有 Statement ID 到物理文件的 SHA 定位、候选 ID 的既有标识、Git 提交引用，与运行时防篡改证明用途不同。本轮复用这些格式即可，避免为了清零 `sha` 字符引发存储迁移。新代码不叠加摘要机制。

保留最短的功能语义：真实几何地址和预算、单一最终物理入口、current 与历史绑定、必要的原子文件替换、已有资源所有者，以及准确的原文对应。字段不匹配、文件缺失等可直接产生普通异常；不写 catch-all 空结果、自动成功回退或通用重试平台。

原测试若只要求已删除的防御行为，可以随代码删除或改成实际行为测试，说明变化即可。针对几何数学、来源和持久化语义的测试继续按改动范围使用。外部服务实际权限留在其已有边缘，本任务的内部简化不改动无关网关授权。

## 8. 变更后维护：用 Git 差分驱动 Host 判断

每次实际开发产生新源码版本后，在需要维护时使用已有 Git 差分提供变化路径和原文窗口，再结合场内已有来源引用寻找受影响理解。初期小场可在维护时做一次直接扫描，无需永久倒排索引或关系数据库。

Host 根据含义选择保留、修订、补充、移动或撤销用途。文件变了不等于判断失效；格式改动也不要求重写记忆。`show/walk` 不附带全仓新鲜度扫描或重新计算状态证明。

沿用现有任务记录保存“已经观察到的源码版本”和“尚未处理的相关变化”。这两个事实与“每条理解都已复核”分开。一次维护未完成时保留具体未处理来源，不因推进一个提交游标丢掉工作，也不新增任务总线或行政账本。

当前 `current=true` 继续只表示场内当前绑定。正文和来源记录表明它根据哪个代码版本形成；需要处理新版本时再核对受影响来源。对代码版本、表达版本和运行时版本分别说明一次，避免共同叫作“最新”。

| E：进取数论应用回归 | 使用固定 EM 来源和独立试验场的通用能力应用记录 | 前提、来源、修订和有条件关系处理正确；工程自举本身不创建科研身份、CLAIM、Activity 或正式 Result。开展实际科研时再按当时 Source 角色与任务执行。 |

推荐把“简化自身存储读取路径”作为首个真实自举开发任务：它跨越存储、Core 构造、Statement 读取和重开行为，目标明确，且直接响应用户要求。项目通用入口可与它一起完成或先用现有 API。下一新会话可接续实现 Git 差异支持的来源维护，或选择更符合当时前沿的真实变化。

公开的推荐任务是开发用例。效果评估另用未参与记忆形成和布局调试的任务，防止把任务答案提前编入场后称为泛化能力。

## 10. 测试范围与对照方法

### 10.1 功能与架构验收

| 场景 | 可观察的通过事实 |
| --- | --- |
| 新会话读取 | 接收者只拿到短入口、任务和资料权限，能在实际场取得理解与固定来源；重启进程本身不代替新的模型会话。 |
| 真实开发 | 提交的补丁满足需求，识别并正确处理必要跨文件条件，相关行为测试支持结论。 |
| 修订后接续 | C1→M1→C2 的行为依赖成立；第二个会话没有依靠第一会话的对话上下文重复答案。 |
| 连接维护 | 实际方向、目标同格其他表达、原位修订和需要时撤桥的结果正确；连接理由可回源。 |
| 状态与安装 | 实际使用场和已安装入口可重开；代码升级不覆盖工作场；删去派生缓存后仍可恢复相同记忆含义。 |
| 防御删减 | 正常操作更直接，重复解析／自证路径确已消除；相关版本与存储行为正确。使用实际调用或轻量诊断展示删减效果。 |
| 原生路径 | Host 从 Surface 选择最终物理入口，关系传播使用现有几何；直接查找和救援路径如实单列。 |

已有通过的分页、连接和修订测试作为受影响回归复用，不重新包装成新发现。扩大测试只为解决实际剩余问题；文档改动不触发全仓运行。若改变 Coverage 数学或可观察存储语义，采用该变化真正适用的现有校准与迁移要求。

### 10.2 同资料模式

| 模式 | 给开发会话的材料 | 回答的问题 |
| --- | --- | --- |
| S：直接来源 | 同一源码、设计、已有文档与正常源码检索，不提供新形成的理解场 | 现行开发方式达到什么效果？ |
| F：同内容平铺 | 与 G 完全相同的理解正文、条件、版本和来源，采用普通字面检索／展开 | 精炼后的理解内容本身带来什么价值？ |
| G：原生关系 | 同批理解的实际几何布局，Surface、单一物理入口、局部／连接展开及回源 | 几何组织相对同内容平铺有什么额外作用？ |

正常开发可以混合使用这些入口，按实际路径记录。G 的发现效果若需要源码搜索救援，任务继续完成，结果记为借助救援完成，保留原生发现缺口。

共同源码材料明确为该次选定的代码、既有设计和相关测试，不含本轮新形成的理解场及其平铺导出、评估答案、其他组轨迹或比较报告。Source 组的普通检索也遵守这个材料范围，避免从同仓新增文件中意外取得记忆组材料；各组均不读取该次答案与其他组结果。用短任务输入约定即可，无需开发权限系统。

对照使用相同源码基线、目标、模型配置与共同入口；记忆组共享相同语义内容，平铺组保留完整关系表达。不要通过削弱基线、为原生组预置目标路径或指定坐标制造优势。若实验采用资源预算，在会话开始前声明，并在各组保持可比；不沿用历史试验的固定三文件等上限作为日常工作限制。

任务应覆盖已知符号定位、未点名的必要跨模块条件、版本变化后修订使用，并按实际失败加入能区分原因的问题。隐藏的是评估题对应答案与预制路线，不是正常记忆中已有的模块名、关系或来源。

形成会话先保存一般项目理解，评估者再选尚未参与形成或布局调整的具体任务。答案判据由源码及行为目标独立给出，不从 Nollm 命中列表反推。已公开例题的成功归入开发回归。实际共享文件系统时，报告“未提供答案材料的新会话”，不声称权限隔离的严格盲试；无需为实验开发新的安全系统。

各组第一项补丁可能不同。比较接续任务时，向所有组提供同一个选定 C1 和对应的同内容 M1，避免将底层代码差别计作记忆效果。真实自举链与这项对齐后的比较分别记录。

### 10.3 测量与解释

首先判定真实修改是否正确，再记录关键条件遗漏、错误迁移、取得了哪些证据。区分“物理上可达”“进入返回列表”“模型实际读取”“最终正确使用”，以便定位改进对象。

成本包含语义形成、几何放置、启动材料、导航、回源、失败与修复、开发、版本维护和后续使用。共同形成成本同时计入 F 与 G；G 另计几何组织成本。已有文档的沉没成本可共用，但新增的整理和自动化费用必须出现。

分别按实际提供的 usage 和计费数据报告其覆盖的 token 与费用；局部 usage 不自动代表完整会话用量或账单。其余记录已观察的字节、调用和耗时，未观察成本保持未知，不把工具字节换算成完整账单。按“形成＋后续使用＋维护”展示累计结果，在相同结果质量下解释投入是否值得。不要只用入库数量、删行数量或接口可调用来宣称效率提高。

## 11. 验收结论与下一轮投资

结论分开写：

- **工程可用性**：真实形成、持久化、回源、冷会话开发及修订后继续开发已经跑通。
- **内容收益**：同内容理解相对直接来源是否帮助减少反复理解、遗漏或实际投入。
- **几何收益**：相对同内容平铺，原生关系在什么任务、什么预算和布局下有额外价值。
- **持续维护成本**：新增源码和错误理解能否局部处理，维护是否吞掉后续收益。

如果 Flat 已有价值而 Native 暂未显示额外收益，保留有效理解，针对已测的原生入口、布局或返回问题继续改进；不把整体成果判成全成或全败。若成本主要被无用摄入吞掉，缩小到实际开发需要的关系。当前阶段优先完成这些可观察闭环，再依据证据决定扩大项目、接入更多宿主或训练专门模型。

功能闭环完成但收益未胜过对照，可以形成有效的理论验证交付；报告应指出改进前沿，而不是预设正结论或人为提升百分比。可运行、产生优势、合并主干和部署线上分别按实际结果报告。
