# Nollm 的架构价值、当前适配器覆盖及规模诊断

日期：2026-11-21。诊断对象：Nollm PR #7 `ddf7dc00b2cea43dccc5d783d20aa88e21de4e0b` 的已安装 runtime。没有修改共享源码、线上场、研究成果或远端仓库。合成场在本地临时目录创建，运行结束后删除。

## 判断

Nollm 值得继续做有边界的探索，最有价值的假设是：**由真实模型形成的有依据命题，通过可修订的几何放置、局部相遇和连接，使另一个研究会话以少量上下文重建研究现场。** 它可以把一部分反复理解、比较和定位的工作提前做一次，供后续问题复用。这个假设符合项目原架构；它不是“模型已经学会进取数论”的证明，也不会免除每次推理读取有关前提的需要。[第一性原理](https://github.com/awdawmip/Nollm/blob/ddf7dc00b2cea43dccc5d783d20aa88e21de4e0b/docs/architecture/NOLLM_FIRST_PRINCIPLES_AND_ANTI_DRIFT_20260711.md)；[项目理解](https://github.com/awdawmip/Nollm/blob/ddf7dc00b2cea43dccc5d783d20aa88e21de4e0b/README.md#project-understanding)。

当前 Enterprise Math 适配器已经提供一个有用的实验入口，但只使用了原架构的一部分。现在最应验证的是：语义放置和原生跨区连接是否比**同一批精炼命题的平面读取**增加了真实研究价值。只与很长的原文比较，容易把“提前精炼”的收益全部归给几何。

本轮也发现了可以直接复现的工程瓶颈：当前默认的三项分页、最高八阶回退和二十四页上限组合，在很小的独立合成场上就可能使明确目标的导航耗尽预算；逐次重放旧路径又放大了调用成本。应先修这一条实际工作链，再以它评判架构。

## 1. 架构职责与当前实际使用

| 层次或机制 | 原架构的职责 | 当前 EM 适配器的情况 |
| --- | --- | --- |
| Core | 语义盲；执行地址、占用、Coverage、局部传播、可逆连接和文件持久化 | 实际使用原生 Core，不是检索结果的几何装饰 |
| Access | 把几何命中的 handle 绑定到命题及原始证据 | `show/source`、当前版本和修订历史已暴露；命题仍要回到固定来源核对 |
| Host | 判断是否同一命题、修订、相关但不同、复用、移动、Stitch 或暂缓 | `save` 的文本和坐标由调用模型选择；适配器只执行 `new` 与 `revision_current` |
| 最终物理入口 | Host 浏览有界 Surface 后明确选一个实际入口 | `walk` 保持此约束；随后从该入口做局部召回 |
| Physical Memory Layer | 实际存放记忆的物理层 | EM 新写入固定为 layer 0，Surface scope 也只包含 `(0,)` |
| Aggregation Order | 从场重建的观察尺度，与物理层不是同一概念 | 实际使用 0–8 阶 Surface；更高阶仍会有多个重叠候选 |
| Coverage | 由物理几何产生的跨层关系；不等于语义父子或证明关系 | 可使用 `coverage_up/down`；即使记忆全在 layer 0，路径仍可上下经过其他层再返回 |
| Stitch / move / reuse / defer | Host 提出可撤回的连接或重新组织，Core 执行 | Access 中已有对应动作；本适配器未开放。召回 kernel 也未包含 bridge |
| Unified Field Encounter | 读取与新命题放置复用同一个相遇过程；区分已有事实、空位、修订和暂缓 | 当前 `save` 接收模型给出的坐标/修订 ID，没有调用完整 Field Encounter 流程 |

代码依据：[EM research.py](https://github.com/awdawmip/Nollm/blob/ddf7dc00b2cea43dccc5d783d20aa88e21de4e0b/lab/nollm-lab/repository_memory/enterprise_math/research.py)、[Access runtime.py](https://github.com/awdawmip/Nollm/blob/ddf7dc00b2cea43dccc5d783d20aa88e21de4e0b/packages/nollm-access/src/nollm_access/runtime.py)、[Field Encounter](https://github.com/awdawmip/Nollm/blob/ddf7dc00b2cea43dccc5d783d20aa88e21de4e0b/packages/nollm-access/src/nollm_access/field_encounter.py)。

据此，不能把现有适配器的短板直接判成整个 Nollm 架构无效；也不能把 Core 内部“有代码”说成用户目前已经获得了完整能力。最值得补上的不是更多入口或治理文件，而是用极薄的研究接口让 Host 能对真实跨线关系做可撤回的连接与局部重组，然后检验收益。

这里的连接仍需附有可回源的数学理由、适用条件和不适用情形。空间接近只帮助找到材料；是否同构、可迁移、已经证明或已正式接纳，仍由科学证据决定。

## 2. 本轮实际运行的诊断

### 方法和范围

使用现有 `enterprise_math.research.save_statement` 逐条写入；每条是约两百字符的英文合成说明，独占一个 layer 0 格子。坐标按紧凑六角区域从中心向外排列。每种规模使用独立临时场，不接触已上线场。

导航使用当前 `walk`、自动初始阶、`steps=1`、`limit=5`、`via=local`。主试验 `page_size=3`；另在 128 条做 `page_size=8` 的接口参数消融。没有修改 Coverage、Core、Host 产品逻辑或已有研究命题。

目标选择器知道合成条目的坐标，并提前从原生几何投影建立一个**仅供诊断的 membership oracle**：每页选择第一个包含目标的候选；否则翻页。它没有理解文字，不是生产语义路由，也没有穷举最短路径。因此：

- 成功证明该策略能够沿实际原生接口进入相应格子并读回目标。
- 失败证明这条明确策略在当前默认预算内失败；**不证明目标绝对不可达**。
- 结果不衡量真实语义召回、数学正确性、创造力或关联发现能力。
- 这些合成放置与离线 oracle 不应迁入产品主路径。

运行环境为 Python 3.12.14、Linux x86-64。打开测试为同进程重复五次；根页为三个新 Python 进程；路径测试为已导入 runtime 的直接函数调用。操作系统文件缓存和进程内可丢弃数学缓存可能已预热。其他工作可能影响机器负载；这些是定位瓶颈的观测点，不是稳定 SLA。

### 建场、打开和根页

| 条目/占用格子 | 逐条建场总秒数 | Core 打开中位毫秒 | 新进程根页中位毫秒 | 0→8 阶占用格子数 | 默认根阶 |
| ---: | ---: | ---: | ---: | --- | ---: |
| 32 | 0.282 | 5.32 | 283.19 | 32,33,33,34,34,35,35,36,36 | 8 |
| 128 | 2.721 | 12.52 | 548.64 | 128,111,100,89,78,67,60,58,56 | 8 |
| 512 | 16.378 | 21.82 | 975.12 | 512,407,340,285,235,193,163,148,133 | 8 |

32 条的小紧凑场在更高阶没有得到更少的非空观察格；128 和 512 条虽有收缩，最高阶仍有 56 / 133 个候选。因此“提高观察阶就必然产生很短的菜单”在这些已测输入上不成立。这是实际投影计数，不是 Coverage 数学错误的证据。

Core 打开本身在这些点上约 5–22 ms；整段交互的瓶颈主要出现在分页、层层下钻和路径重放。逐条写入还会反复读取、序列化完整 Core 状态，现实现对更大场有增长压力，但三组小样本不能给出可靠的大规模吞吐外推。[Core state](https://github.com/awdawmip/Nollm/blob/ddf7dc00b2cea43dccc5d783d20aa88e21de4e0b/packages/nollm-core/src/nollm_core/state.py)、[storage](https://github.com/awdawmip/Nollm/blob/ddf7dc00b2cea43dccc5d783d20aa88e21de4e0b/packages/nollm-core/src/nollm_core/storage.py)。

## 3. 为什么会触发二十四页错误

[surface_selection.py](https://github.com/awdawmip/Nollm/blob/ddf7dc00b2cea43dccc5d783d20aa88e21de4e0b/packages/nollm-access/src/nollm_access/surface_selection.py) 定义：

```python
RECALL_SURFACE_BUDGET = SurfaceBudgetProfile(8, 4, 32, 8, 4, 160, 8, 8, 24)
```

按字段依次为：每页 8、估计页数上限 4、Surface 格子上限 32、页开销 8、格子预览开销 4、投影总单位 160、下钻深度 8、最高阶 8、Surface 调用上限 24。

EM 入口默认只把页宽改成 3；其余预算保留。选初始阶时，任何一阶都不满足页数/格子/投影预算，就回退到最高阶并在内部记 `overflow=True`。当前 EM 返回的简化 JSON 没把这个 overflow 和估计页数带给调用模型。四页是**选择初始阶的估计目标**，不是四页后立即拒绝；真正后续执行触发的是 Surface 的 24 次计数上限。

本轮 32 / 128 / 512 在最高阶预计分别需要 12 / 19 / 45 个根菜单页，均超过最初四页目标。128 的中心目标第 24 个成功返回页仍在 order 1；下一次下钻试图进入 order 0，抛出 `RuntimeError: Surface traversal call limit reached`。512 的中心目标第 24 页仍在 order 7。最终物理入口选择本身不再增加页面计数。

此外，[coverage_cli.surface](https://github.com/awdawmip/Nollm/blob/ddf7dc00b2cea43dccc5d783d20aa88e21de4e0b/lab/nollm-lab/repository_memory/coverage_cli.py) 每次从头重放全部 `choices`；每个新页又重新打开 Core、计算活动观察面、生成预览。对成功的 128/page 8 中心目标，14 次接口调用合计重建了 104 个已计页面；对失败的默认中心目标，24 个成功响应已累计 300 个页面计数，尚不含失败请求再次重放的工作。这是可以优先消掉的重复成本。[Surface navigator](https://github.com/awdawmip/Nollm/blob/ddf7dc00b2cea43dccc5d783d20aa88e21de4e0b/packages/nollm-access/src/nollm_access/surface_navigation.py)。

## 4. 直接可执行的改善目标

| 优先项 | 最小改进方向 | 验收证据 |
| --- | --- | --- |
| 把导航预算状态说清楚 | 返回选阶的 overflow、预计菜单页数和剩余页面预算；预算耗尽返回可继续决策的信息 | 128/512 的失败输入能解释失败位置和余下选择，不让 Host 误以为已搜索完或目标不存在 |
| 消除整段旧路径重放 | 复用现有 `state_to_mapping/state_from_mapping` 或等价的可丢弃导航状态，让下一页从当前页继续；不另建语义索引 | 冻结场和相同 choices 下，候选、最终入口和 recall 相同；页面构建随新增页面线性增长，先在 128 点复测 |
| 选择实际更合算的观察阶/页宽 | 把最高阶 overflow 当成需要选择的情况；比较有依据的不同初始阶、页宽或允许的直接下钻 | 至少让本轮 128 三目标在合理预算内完成；同时报调用数和输出量，不只扩大上限 |
| 提高观察提示的代表性 | 当前是按稳定坐标排序取最多三条、截 256 字符，EM 又只展示首行；需要检验这些线索是否能代表大片区域 | 新会话不知道目标坐标时，能够依据预览选择有用方向；与同内容基线比较，并保留真实前提和来源 |
| 以实际需求接上原生连接 | 用极薄接口暴露已有 Stitch/撤销、局部移动或统一 Encounter 的必要部分；避免重造大平台 | 一个冻结的跨区复用任务，在移除该连接后变难，恢复连接后受益，且没有把关联当作证明 |

这些是待实施/待验证的方向。本轮没有声称已经修复。无需重写几何核、增加新哈希/审计体系或恢复所有历史工作流。若有会改变 Coverage 输出的数学变更，应另立任务，而不是混进这次导航优化。

“提示代表性”应在 Host/Access 观察面解决，并可删除后从原场重建；不能另造一个全局语义路由表再把几何挂在后面。新增区域说明也要与命题事实和原始证据区分。

## 5. 哪些测试真正决定是否继续投入

### A. 区分精炼收益与几何收益

同一批冻结原文，由相同 formation 过程形成命题。比较：原文直接读取；同一批命题的平面读取/字面搜索；原生 Nollm。题目和答案不进入 formation，读题的执行会话不继承整理者上下文。三臂都允许用同样方法回到原证据。记录正确性、前提遗漏、真实跨线使用、无效类比、调用数、模型输入输出、来源展开及 formation 成本。

若 Nollm 只胜过长原文、没有胜过同内容命题，那么“持久化精炼记忆”有价值，几何增益仍未证实。这个结果应缩小近期研发范围，不应再用不断扩充接口掩盖。

### B. 原生关系的因果消融

同一命题、同一来源、同一查询预算，比较经过理由说明的放置、打乱放置、相关连接开启/撤销。只把这些改变用作实验条件，不把随机放置变成产品行为。题目至少包含：关键词不相近但前提匹配的有效迁移；词语相似但结构条件不满足的陷阱；连接只给线索而结论仍未知的情形。

若合理放置/连接不能持续改善这些任务，就不能把几何视作有效研究记忆的必要部分。反过来，若在新题上它稳定找到平面检索遗漏的有用关系，且证据与总成本可接受，才有理由把主投资放在这条路线。

### C. 研究生命周期与累积成本

让不同会话反复提出新问题，而非多次问相同题。包括过时猜想被修订、错误类比撤销、一个局部命题新增适用条件、两个看似相同结果后来发现前提不同。保存“为什么要记、放在哪里、为什么连接”的简短科学理由。以总成本比较：初次 formation + 后续修订 + 全部任务的理解、导航、回源和复核成本。

只有命题被多次真实复用，初始理解成本才能摊薄；重复问已知答案不能代替这个证据。历史仓库性能材料已证实省掉重复建场和重复绑定读取有工程收益，但该材料也明确没有证明语义选入口质量。[已有 FIELD_PERFORMANCE](https://github.com/awdawmip/Nollm/blob/ddf7dc00b2cea43dccc5d783d20aa88e21de4e0b/lab/nollm-lab/repository_memory/comparison/FIELD_PERFORMANCE.md)。

### D. FREE A 的独立问题形成

单独测试当前允许基础输入下的自由选题，并保留自主问题形成后、候选冻结前的精确定义/条件/工具查询；候选冻结后再接入完整成果比较，发现联系、撞题和已有反例。比较不同允许视图介入的效果并记录实际曝光，不增加一刀切的已有知识禁读。判断是否减少重复劳动、是否提供可验证的新问题、是否把所有问题吸向同几条已有路线。这个 Host 模式选择应与普通 TASK 模式分开；不需要把防锚定规则变成 Core 的内容准入分类器。

## 6. 对前途与投入方式的判断

近期应把 Nollm 当作一个**需要真实研究任务证明价值的外部记忆实验**。最有希望的产品形态是：薄入口、可复用的命题、保留证据、有限局部相遇、可撤回的跨线连接、新会话能够接着研究。持续增大上下文不是这个形态的验收指标。

暂不建议靠扩大数据灌入、增加一套治理平台或立刻训练辅助小模型来解决当前问题。现在已经可以定位到导航预算、观察提示、重复重放和未用上的连接能力；这些先做小实验即可检验。等实际使用积累了“哪些命题值得记、哪些放置有效、哪些连接错误、哪些条件易漏”的可靠样本，才有依据判断是否需要一个专职 formation/导航模型。那时也要与同接口下的当前 Host 比较，不把训练本身当成成功。

适合继续投入的证据是：不同新会话在未见过的真实题上复用对的关系、少漏条件、能拒绝错误迁移，且 formation 加查询加修订的总成本逐渐下降。若目前几何不能给出这种增益，就应保留已经有价值的命题与证据资产，收缩几何路线的投入，继续保留可复算实验记录。

## 复现材料

- `scale_navigation.py`：唯一诊断脚本，调用既有 runtime；不包含新的性能框架。
- `scale_32.json`、`scale_128.json`、`scale_512.json`：默认分页原始结果。
- `scale_128_page8.json`：页宽消融。

示例：

```sh
python scale_navigation.py --runtime /path/to/installed/scripts/runtime --size 128 --out scale_128.json
python scale_navigation.py --runtime /path/to/installed/scripts/runtime --size 128 --page-size 8 --out scale_128_page8.json
```
