# 仓库记忆开发任务对照

2026-11-18，对 Nollm 同一提交的三个改动需求分别开设独立会话。每个需求的三名参与者从同一份源码出发，实现同一接口。直接搜索和全景两组均通过三个任务的全部检查。自动入口组通过两个，第三个遗漏了 Core 的公开接口契约。仅根据这组数据，把几何召回设成所有改动的默认步骤缺乏依据。

## 主实验

| 改动及验收口径 | 直接搜索 | 先读全景 | 自动入口及原生召回 |
| --- | ---: | ---: | ---: |
| 查询一个绑定的当前及支持语句，覆盖 Store 与 Runtime | 5,230 · 11/11 | 5,335 · 11/11 | 5,738 · 11/11 |
| 导出语句规范字节，覆盖对象、存储及旧记录 | 1,484 · 10/10 | 1,892 · 10/10 | 2,288 · 10/10 |
| 将条件写入的状态摘要提取到 Core 公开接口，涉及 Core、Access、快照和接口清单 | 10,710 · 21/21 | 10,725 · 21/21 | 11,945 · 20/21 |
| 三个独立会话的观察文本 token 合计 | **17,424** | **17,952** | **19,971** |
| 全部验收与回归同时通过的任务 | **3/3** | **3/3** | **2/3** |

每格给出实际交付给参与者的起始包、搜索输出及源码读取的分词数，后接通过的检查数。使用 `gpt-tokenizer@3.4.0` 的 `o200k_base` 对每次原样输出单独分词，重复阅读按次数计入。会话包装、历史重复发送、推理、生成补丁以及个别参与者自行运行的验证命令均在这个仪表的观测范围之外。宿主没有暴露供应商用量，成绩里的 `provider_usage` 为 null。运行在有用量回执的平台时，可以在评分前保存该会话的真实 `usage.json`，至少包含 `model`、`input_tokens`、`output_tokens`。

前两个任务的全部参与者都打开并引用了两个必需源码文件。摘要任务另需更新已存在的公开接口清单。直接、全景、自动入口三组依次打开并引用了 3/3、3/3、2/3 个必需文件。其提交的引文总数依次为 6、7、7，包含额外的测试和接口来源。评分器单列必需来源覆盖率和必需来源占引文的比例。增加合理的旁证也会使后一个比例降低。

摘要任务的自动入口是 `snapshot.scope`，一步邻格召回还返回了 `statement.retry` 和 `recall.evidence`。这名参与者正确实现摘要并通过两个隐藏功能测试，现有的 `test_core_runtime_public_operations_match_allowlist` 揭示了遗漏。其余两个任务都选了 `recall.evidence`，两次拿到相同三条说明。五条说明的储备、入口选择和表述格式共同影响本次结果。

## 改进后的复测

原生详细 JSON 给出了核阅版本、Git blob 和遍历路径。全景的紧凑格式按行展示说明与缩写 blob。为观察输出格式造成的开销，将同一批原生结果重新渲染成全景使用的行格式。只替换起始包，三个任务分别从 912、916、889 token 降到 380、391、375 token，顺序为绑定、导出和摘要。这组差值不涉及任何模型重跑。

随后分别用新的独立会话实作绑定和导出任务。紧凑召回的完整观察读数为 **5,042** 和 **1,763**，验收与回归分别为 **11/11** 和 **10/10**，都找齐了两个必需文件。绑定任务的读取范围与原 JSON 组有所不同，因此表中会话总数还反映了参与者的阅读选择。

最后根据失败的公开接口检查，新写了一条核阅说明，绑定真实测试、接口清单和 Core 源码。保留原五条说明，用补充后的清单和紧凑格式再开一个摘要任务会话。新入口返回接口规则，该参与者打开并引用 **3/3** 个必需文件，通过 **21/21** 个检查。观察读数为 **10,239**，其中起始包 **244** token。这次定向修复使用了前次失败所暴露的知识，单独报告，原三组成绩保持有效。修复对其他公开 API 改动的迁移价值仍待新任务验证。

另用 [time_packets.py](time_packets.py) 轮换三道任务，每组新建 12 个输入包。在本机已有文件缓存的条件下，起始包构建中位数为直接 0.02 ms、全景 61.3 ms、原生 JSON 259.9 ms、原生紧凑 279.4 ms。计时范围止于输入包构建，完整开发会话的执行时间尚未计量。可用 `python "$C/time_packets.py" --repeats 4` 重测。

## 复现和评分

基础版本固定在 `314eb47490adcad22e37d6e05d2da3983e78956d`。任务原文在 [compare.py](compare.py)。基线只有任务文本，全景组另得五条已有说明，原生组把原样任务作为查询，读取当时默认的完整 JSON。三组都可自行搜索或回源。每次试验使用单独的包源码和已有测试副本，摘要任务的副本还含仓库原有的 Core 公开接口清单。判分代码和其他参与者的结果位于试验副本之外。本轮没有提供答案文件列表。

在分支仓库根目录运行以下命令。需要 Git、Python 3.12、ripgrep、pytest、Node.js，以及可由 Node 加载的固定版本分词器。分词器只用于基准计量，正常使用 skill 无须安装。

```sh
C=lab/nollm-lab/repository_memory/comparison
T=$(mktemp -d)
python -m venv "$T/venv"
"$T/venv/bin/pip" install pytest==9.2.0
npm install --prefix "$T/tokenizer" --no-audit --no-fund gpt-tokenizer@3.4.0
export NODE_PATH="$T/tokenizer/node_modules"
"$T/venv/bin/python" "$C/compare.py" prepare --task digest --arm field --trial "$T/trial"
(cd "$T/trial" && python observe.py start)
```

每个任务与组别都用一个新目录和独立会话。给参与者试验目录，让其先执行 `python observe.py start`，仅用 `python observe.py search REGEX` 和 `python observe.py read PATH [FIRST [LAST]]` 取材，在 `tree/` 修改源码或必要契约，用相对路径数组写出 `evidence.json`。查看工具结果时给足输出长度。参与者交卷之后，由评估者运行以下命令。验收有一项失败就返回非零，并保留差异和分数。

```sh
"$T/venv/bin/python" "$C/score.py" --trial "$T/trial" --out "$T/result"
```

[acceptance.py](acceptance.py) 中每个任务有两个独立行为测试。[score.py](score.py) 还按任务运行 9、8、19 个原有检查。未打补丁的基础版本在全部六个新增检查上失败，原有 36 个检查全部通过。每组只有一名参与者处理每个任务，任务明确给出了目标接口名称。准确率和成本结果适用于这三个局部改动。对未知符号定位、大仓库、长期维护成本及重复试验的方差还需另测。

单独提供的证据压缩包内含基础源码快照、每次试验的初始包、原样阅读记录、补丁、来源声明、逐项成绩和复算脚本。解压后，在包根目录使用下列命令逐项重放工具输出、分词和验收。失败样本应当重现同一项失败，重放过程将其视为与记录一致。

```sh
"$T/venv/bin/python" comparison/replay.py --snapshot source.tar.gz --receipts receipts
```

若要同时核对当前分支生成的起始包，可在 Nollm 分支根目录执行 `python "$C/replay.py" --repo . --receipts /path/to/extracted/receipts`。这条命令需要同版本的 pytest 与分词器。
