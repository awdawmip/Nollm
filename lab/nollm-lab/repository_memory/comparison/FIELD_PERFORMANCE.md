# 原生场复用的端到端耗时

同一份说明可以回答不同的开发问题。旧版每次都按证据布局、写入全部语句与绑定，再从物理入口召回。新版在 Git 证据仍匹配时打开上次建好的原生场。每次查询仍核验 Git 版本、按任务选入口，并从 Core 与 Access 读取结果。

## 测量结果

2026-11-18 在 Linux x86-64、Python 3.12.14 上运行。单位为毫秒。

| 新鲜说明 | 查询位置 | 旧版中位数 | 新版中位数 | 旧版 p95 | 新版 p95 |
| ---: | --- | ---: | ---: | ---: | ---: |
| 5 | 首次 | 318.34 | 366.68 | 525.93 | 534.31 |
| 5 | 后续 | 361.36 | 273.53 | 977.38 | 556.47 |
| 40 | 首次 | 729.85 | 779.87 | 867.99 | 899.76 |
| 40 | 后续 | 756.34 | 238.19 | 937.68 | 348.40 |

5 条和 40 条组的后续查询中位数分别下降 **24.3%** 和 **68.5%**。首次查询仍要生成完整场，并原子发布供以后复用，本轮中位数分别增加 48.34 ms 和 50.02 ms。每个查询都启动一个 CLI 进程，表中绝对时间会随机器负载、磁盘及 Python 环境波动。

在计时之外另取一次 40 条组后续查询做 cProfile。旧版调用 `put_statement` 和 `apply` 各 40 次，新版这两项均为 0 次。新版核验 Git 说明用了 10.83 ms，选入口 14.73 ms，打开并读取原生场 19.09 ms。Python 模块导入仍占用新进程启动时间。各调用的累计耗时可能包含子调用，不能直接相加。当前宿主选入口仍随清单规模扫描说明，所测加速来自省掉重复建场以及减少绑定文件读取。

两种规模共比较了 **64 对**计时响应的完整 JSON 字节，均一致。在已有缓存的同一仓库中，单独提交对辅助证据 `handle_store.py` 的改动后，两版均停止返回 `recall.evidence`。5 条组返回 `no_match`，40 条组还能从其他新鲜说明选入口。显式切回原版本，两组都恢复完全相同的入口、正文、证据和遍历路径。此次候选运行源码指纹为 `f37d43c90c80cc6d1757dc520db1ed560447bb7e3289d11bd096dac7b366feee`。

## Access 绑定读取

另外在已经打开的原生运行时上，预置 64 个真实绑定，以同一入口取回 7 个邻域条目。每版重复 50 次。一次召回对绑定文件的读取从 7 次降至 1 次，JSON 解码从 14 次降至 1 次。50 次召回的中位数从 **23.22 ms 降至 2.14 ms**，p95 从 **39.56 ms 降至 3.08 ms**。两版 7 个条目的完整结果序列化后 SHA-256 均为 `85b0782480c92f50ffd6b81dc306be16c0cf4e5d2354593933cc92baa43338f1`。此项计量限于 Access 方法调用，进程启动和建场开销在上面的 CLI 表中另有计量。[Access 复算脚本](time_access_recall.py)

## 如何复算

在含有旧版本 Git 对象的 Nollm 分支根目录执行以下命令。只需要 Python 3.12 和 Git，试验目录在运行结束后清理。

```sh
D=lab/nollm-lab/repository_memory/comparison
python3 "$D/benchmark_field.py" --repo . --sizes 5 40 --rounds 8 --out /tmp/nollm-field-speed.json
```

脚本从 Git 对象导出旧版 `b2680557d8452b8ab66179d1626fda4c86407976`，并在计时前复制当前 checkout 的 skill 启动器、实现模块和 Core/Access 源码。输出记录候选代码指纹、每次调用耗时、分位数、完整响应的 SHA-256、cProfile 调用记录与失效检查。源码样本和说明的核阅依据固定在 `314eb47490adcad22e37d6e05d2da3983e78956d`。

5 条组使用原先的人工说明。40 条组保留相同五条，另从同一提交中 35 个不同 Python 模块的语法树各生成一条结构说明，引用定义所在文件的 Git blob。这些补充样本用于增加读取和建场工作量。语义选入口的质量仍由独立的真实改动试验评估。

每组、每轮新建一个临时 Git 仓库。每次调用都从独立 Python 进程经 `scripts/memory.py recall` 正常入口执行，计时含启动、Git、原生 I/O 和完整 JSON 输出。四个查询分别覆盖当前绑定、写入重试、快照和证据召回。轮换哪一题先问，并交替旧版和新版的执行顺序。首次指该仓库尚无物化场，随后三次查询使用不同问题。操作系统文件缓存和 Python 字节码已预热。每版每种规模含 8 个首次样本、24 个后续样本。p95 取最近秩，因此首次查询的 p95 等于该组观测到的最大值。
